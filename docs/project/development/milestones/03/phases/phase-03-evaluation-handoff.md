## Scope and outcome

The [CUDA evaluation and application handoff](/docs/project/development/milestones/03/cuda-gpu.md)
assesses numerical agreement, repeatability, failure safety, usability and performance separately.
It links the qualified source and retained primary-PC evidence, explains storage and arithmetic
decisions, and defines the accepted-snapshot boundary for future application integration.
The roadmap now links that assessment without starting application or rendering implementation.

The observed benefit is conditional: at 8,000 particles CUDA takes 7.611185 s for 480 completed
steps, 8.381× faster than fresh serial grid and 2.827× faster than the fixed twelve-worker control.
CUDA loses to serial grid at 64 and 216 particles. Exact agreement preserves the reference
calculation; it does not demonstrate improved physical accuracy or a rendered frame rate.

## Decisions and documentation

The public CUDA and usage guides already explain optional builds, device/block selection, replay
identity, ownership and errors. Linking their full assessed revision preserves reproducibility
without changing any of the campaign's 99 simulator file hashes. The evaluation adds the synthesis
and integration responsibilities those guides do not own. No code, arithmetic, tolerance, fixture,
golden, dependency or numerical contract changed.

The arithmetic account retains both rejected power controls and the supported host-rounding
adaptation, rather than presenting exact agreement as automatic GPU behaviour. Storage analysis
distinguishes checked capacity from demonstrated capacity: membership is quadratic even for sparse
inputs, and neither peak memory nor a maximum feasible size was measured. Profiles establish stage
costs but do not isolate kernels, transfer costs, GPU utilisation or host waiting. Cancellation
examples retain exact accepted prefixes without claiming a worst-case response bound.

The handoff uses immutable accepted host snapshots and synchronous completed calls. CUDA contexts
are neither `Send` nor `Sync`; a future simulation thread must construct and own its solver, passing
owned snapshots to presentation. Rendering cadence must preserve fixed simulation work, while
CPU/GPU controls, independent audits, fixtures and comparison evidence stay available. Graphics
interoperability and zero-copy presentation remain future work requiring their own ownership,
correctness and timing qualification.

## Verification

Fresh local verification on 20 October 2026 used Rust/Cargo 1.98.1 and Python 3.12.3 on x86_64
WSL2 with glibc 2.39. The [retained checks](/docs/project/development/milestones/03/assets/evaluation-v1/README.md)
contain exact command arguments, exits, elapsed times, stdout/stderr and source identities.
From the EPQ root:

```sh
cargo test --manifest-path Maelstrom/Cargo.toml --release --locked --offline --no-default-features --quiet
python3 -m unittest discover -s tests -p 'test_*.py'
python3 -m unittest discover -s tests/baseline -p 'test_*.py'
python3 -m unittest discover -s tests/verification -p 'test_*.py'
python3 -m tools.cuda.performance report \
  docs/project/development/milestones/03/assets/performance-comparison-pc-v1/campaign
python3 tests/evidence/checks/cuda_performance.py \
  docs/project/development/milestones/03/assets/performance-comparison-pc-v1/campaign
```

All **208 release CPU Rust tests**, including two doctests, and **47 parent tests** passed. The
independent audit rechecked all 105 clean complete benchmark attempts, three golden results,
21 profiles, 99 source hashes, nine collector hashes and the full physical observations/statistics.
The comparative report regenerated byte for byte and its stored JSON matched recomputation.
Both 99-file source manifests matched their full committed revisions; all 431 assets indexed by
the original solver and performance integrity manifests matched their hashes. Local document
links and structure were checked. Raw historical evidence was preserved.

## Limitations and Gate G03

Local evaluation and handoff work is complete. **G03 remains pending its separately authorised
completion checkpoint.** The existing EPQ gitlink already pins the assessed Maelstrom revision;
neither repository was committed, tagged, switched, pushed or otherwise checkpointed during this
work. Intended completion tags are `milestone-03/phase-03/complete` and `milestone-03/complete` in
both histories, following implementation-first verification and checkpointing when authorised.

No fresh PC benchmark or hardware test, alternate-device/platform qualification, physical-accuracy
study or hosted rendering check was performed. Previously unavailable Compute Sanitizer memcheck
and racecheck remain unavailable, and actual device-loss recovery remains unqualified. The
evaluation keeps those limits, the tested launch/duration envelope and uncontrolled measurement
conditions explicit. Application integration, rendering and the final project comparison remain
outside this phase's implemented work.
