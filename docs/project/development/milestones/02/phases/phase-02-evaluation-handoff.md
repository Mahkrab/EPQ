# Phase 2 evaluation, documentation and CUDA handoff

## Starting point

Work began from clean EPQ `d51e95fa300d41dec14add1e509fd3dd89a7d933` and Maelstrom
[`60b9a767636428a26f39a1901e2cac4276c75c83`](https://github.com/Mahkrab/Maelstrom/tree/60b9a767636428a26f39a1901e2cac4276c75c83),

## Scope and outcome

The [milestone evaluation](/docs/project/development/milestones/02/threaded-cpu.md) assesses numerical
agreement, repeatability, transactional safety, public usability and performance separately, linking
the assessed source, independent tests and retained results. It explains work distribution and
resources, evaluates overhead and saturation, and defines the CUDA handoff. The local documentation
work and the subsequently authorised local completion checkpoint are complete.

The measured result is conditional: suitable worker counts improve the larger tested workloads,
reaching 2.988× against fresh serial-grid controls at 8,000 particles with twelve workers. All 245
benchmark attempts agree exactly with serial controls. One worker is slower than serial throughout;
twenty-four workers incur severe small-input overhead and are slower than twelve at the largest size.
The capacity-based default therefore does not establish an optimal count.

## Decisions and documentation

The existing public usage guide already documents explicit/default selection, effective counts,
private pools, replay, library APIs and failure behaviour. The evaluation links that exact revision
and summarises its supported contract. Maelstrom documentation and all 82 hashed source files remain
unchanged, preserving direct reproducibility of the retained campaign. The campaign README now links
the evaluation and distinguishes its measurement checkpoint from the final milestone boundary.

Concurrency safeguards are explained through immutable snapshots, complete-pass barriers, ordered
per-particle reductions and joined error collection. Deliberately incorrect test controls are
identified as controls, not invented defect history. Profiles establish remaining stage costs;
bandwidth, cache, imbalance and scheduling explanations remain hypotheses where unmeasured.

The CUDA handoff retains CPU controls, physical identities, fixtures/goldens, comparison reports,
stage oracles, membership rules, diagnostics and atomic acceptance. It separates these obligations
from CPU-specific Rayon scheduling, worker limits and storage choices. Changed reduction order needs
explicit component-level qualification under the existing comparison policy; compact hashes cannot
justify tolerance acceptance. GPU setup, transfer and synchronisation boundaries must be declared
before a future comparison. No GPU infrastructure was added.

## Verification

Fresh local verification on 18 October 2026 used Rust/Cargo 1.98.1 and Python 3 on x86_64 WSL2 Ubuntu
24.04.5. From the EPQ root:

```sh
cargo test --manifest-path Maelstrom/Cargo.toml --release --locked --offline --quiet
python3 -m unittest discover -s tests/baseline -p 'test_*.py'
python3 -m unittest discover -s tests/verification -p 'test_*.py'
python3 -m tools.verification.main report \
  docs/project/development/milestones/02/assets/verification-v1
python3 -m tools.baseline.scaling report \
  docs/project/development/milestones/02/assets/performance-scaling-pc-v1
python3 tests/evidence/checks/scaling.py \
  docs/project/development/milestones/02/assets/performance-scaling-pc-v1
```

All **204 release Rust tests**, including two doctests, and **31 parent tests** passed. The 36
retained component comparisons regenerated successfully with exact agreement. The independent PC
audit rechecked all 245 attempts, seven correctness results, 49 profiles, 82 source hashes and five
collector/protocol hashes, finding no unclean or timed-out attempt. All eight campaign Markdown
reports regenerated byte for byte, and the stored component and independent audit reports matched
recalculation. Local document links and structure were checked. No retained raw evidence changed.

## Limitations and Gate G02

The evaluation states the tested envelope and accepted limits: dense storage, cancellation latency,
unmeasured memory and adversarial performance, independent audit cost, host variability and unknown
causes of two backward UTC transitions. Monotonic durations remain the measurement basis. No new
PC benchmark, GPU, cross-platform, hosted-rendering or physical-accuracy verification was performed.

The evaluation, handoff and local completion checkpoint satisfy **G02**. Annotated
`milestone-02/phase-02/complete` and `milestone-02/complete` tags identify the completion boundary
in both repositories, following the implementation-first sequence in the owning plan. The existing
gitlink already pins the assessed Maelstrom commit; no simulator change or new implementation commit
was needed. Remote publication, hosted verification and completion of the wider project remain separate.
