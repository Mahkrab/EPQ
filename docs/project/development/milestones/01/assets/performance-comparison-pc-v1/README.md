# Paired PC search comparison

This campaign compares serial brute-force and uniform-grid discovery on the primary PC reached
through `ssh pc`: an AMD Ryzen 9 7900X under x86_64 WSL2 Ubuntu 24.04.5. Collection ran on
17 October 2026 from 16:18:26 to 16:39:12 UTC. The two backend directories and generated comparison
were imported byte for byte from the PC; this explanation and independent validation were added later.

## Results and retained files

The [comparison report](/docs/project/development/milestones/01/assets/performance-comparison-pc-v1/report.md)
and [machine-readable comparison](/docs/project/development/milestones/01/assets/performance-comparison-pc-v1/comparison.json)
retain the seven-size outcome. The grid's primary medians are slower through 1,000 particles, then
faster at 1,728, 4,096 and 8,000. At 8,000, the brute-force/grid medians are 90.021109/55.621480 s,
giving 1.618× speedup. Near-equal medians at 512 and 1,000 and overlapping sample ranges do not
establish a precise crossover; the observed median crossover lies between 1,000 and 1,728.

Each backend retains its [brute-force report](/docs/project/development/milestones/01/assets/performance-comparison-pc-v1/brute-force/report.md)
or [grid report](/docs/project/development/milestones/01/assets/performance-comparison-pc-v1/uniform-grid/report.md),
`dataset.json`, initial `collection.json`, replayable `correctness.json` and all 35 `raw/` attempts.
Together these contain 70 full benchmark attempts: one warm-up, three primary samples and a separate
profile for each size/search. All completed 480 steps without warnings, failures or timeouts. Every
complete attempt matches its same-size brute-force warm-up exactly after the declared metadata
exclusions, including sign-sensitive input/snapshot hashes, every checkpoint audit and CFL outcome.
Both separate 64-particle correctness results also match the frozen golden.

The [independent validation](/docs/project/development/milestones/01/assets/performance-comparison-pc-v1/validation.json)
records checks made without importing collector code: raw hashes, all 80 source hashes against the
commit, frozen fixtures, complete physical-output comparisons, primary statistics, throughput, stage
sums/proportions and speedup arithmetic. Backend and comparison reports regenerated byte for byte.

## Method and provenance

Both searches use clean Maelstrom
[`b179e6e42b4efd6e269d6eb35fbee50dba4fcfa1`](https://github.com/Mahkrab/Maelstrom/tree/b179e6e42b4efd6e269d6eb35fbee50dba4fcfa1),
one binary and the unchanged `serial-baseline-v1` and `reference-comparison-v1` policies. Rust/Cargo
1.98.1, the standard release profile, no custom flags, factor-four refinement, eight Jacobi passes,
checkpoints 0/1/120/240/480 and the 120-second budget plus 30-second grace are recorded in both indexes.
All search construction, ordering and required validation remain inside the measured timestep.
Profiles have extra clocks and do not supply primary speedup ratios. Available guest memory is
environment context; process memory was not measured.

The PC's existing checkout remained unchanged. Separate temporary checkouts came from bundles of
EPQ `78652854eb22cd7985e8e2e22af7595f977bc011` and the assessed Maelstrom commit. Eighteen collector
tests and the full release Rust suite passed before collection. No other project checks ran on the
PC during measurement. The final 19-test collector suite passed there after collection.

The indexes identify the uncommitted collector by file hashes. `main.py` and `data.py` match the final
working files. The recorded protocol bytes match the EPQ base above; the current protocol adds the
paired-search clarification without changing policy. The recorded `compare.py` predates a two-line
interruption guard added during review: after `baseline.collect`, the final code checks the retained
`interrupted` flag and stops before starting another search. Removing that guard reconstructs the
recorded bytes exactly. All retained campaigns were uninterrupted; the correction changes neither
their invocations nor their qualification or reporting. These provenance checks were made locally.

## Reproduction and limitations

From an EPQ checkout containing the collector and the identified Maelstrom implementation, on the PC:

```sh
RUSTUP_TOOLCHAIN=1.98.1 python3 -m tools.baseline.compare collect NEW_DIRECTORY
python3 -m tools.baseline.compare report NEW_DIRECTORY
```

From the current EPQ root, regenerate this comparison without simulation:

```sh
python3 -m tools.baseline.compare report \
  docs/project/development/milestones/01/assets/performance-comparison-pc-v1
```

The full correctness results replay from the Maelstrom checkout with `./target/release/maelstrom replay
PATH_TO_CORRECTNESS_JSON --format json --quiet`. Replay restores each recorded backend and runs without
measurements. Dataset command arguments retain every workload request; original reference goldens and
input hashes remain in Maelstrom. Collection requires a new directory and never overwrites this campaign.

Brute force ran before the grid, with no frequency, affinity or priority controls. Shared WSL/host
load, scheduler migration and thermal state remain confounders. Three samples describe observed
variation, not statistical significance. The largest tested size was 8,000; neither backend reached
the invocation budget, and no larger series was collected. No practical maximum, memory reduction,
cross-device speedup or improved physical fluid accuracy follows. The older
[PC baseline](/docs/project/development/milestones/00/assets/performance-baseline-pc-v1/README.md)
remains separate and is not used as the speedup denominator.
